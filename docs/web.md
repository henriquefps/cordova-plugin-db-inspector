# Web version

**Live:** https://db-inspector.hfps.dev (demo: https://db-inspector.hfps.dev/?demo)

The same inspector UI (`www/inspector/db-inspector.html`) also runs as a static website. It inspects SQLite files **on the user's own machine**: someone opens the page, drops a `.db` file on it, and gets tables, structure, the query builder and presets, just like inside the app.

## How it works

```
index.html (db-inspector.html + host.js)
   │ invoke(callId, action, args)            ← the same bridge contract as Android / iOS
   ▼
worker.js (Web Worker)
   │ same actions and JSON shapes as the native engines
   ▼
wa-sqlite (SQLite → WebAssembly) + LazyFileVFS
   │ reads only the pages SQLite asks for: FileReaderSync + File.slice()
   ▼
the user's local file (never uploaded, never modified)
```

- **Nothing is uploaded.** The site is static files only. The `File` object stays in the browser, and the worker reads it in place.
- **Enforced by the browser.** `_headers` sets a strict Content-Security-Policy: `default-src 'none'`, `connect-src 'self'` (only the site's own `.wasm` and demo file), the inline script pinned by its SHA-256 hash, `form-action 'none'` and `frame-ancestors 'none'`. The page can't send data to any other origin, even if its code were changed in the browser.
- **Large files.** The VFS reads 64 KB blocks on demand, with a 32 MB LRU cache. A 433 MB OutSystems database opens in well under a second and uses about 10 MB of JS heap. A full `PRAGMA quick_check` over it takes about 4 s.
- **Read-only.** Connections are read-only, and the VFS refuses writes to the database. Temp files (sorting, temp b-trees) live in memory.
- **WAL.** When the user adds `x.db` and `x.db-wal` together (or the `-wal` later), the WAL is applied as an overlay. Frames are validated exactly as SQLite does (salts and checksum chain), and only frames up to the last commit are used. WAL-mode files are then presented to SQLite in rollback mode, so it never looks for a `-shm`.
- **Export.** *Info → Export database file* downloads a single consistent file. With a WAL present, it is composed lazily from `Blob` slices: main-file pages plus the newest WAL page versions, which costs no extra memory.
- **Cancel.** A running statement can't be interrupted from outside the worker, so **Cancel** replaces the worker. Re-opening is instant thanks to lazy reads.
- **Storage.** Presets, history and preferences live in `localStorage` (per browser, per site).

## Differences from the app

| | App (plugin) | Web |
|---|---|---|
| Databases | Every SQLite file in the app sandbox | Files the user opens or drops |
| Close button | Closes the screen | Hidden |
| Save / export | Android save dialog, iOS share sheet | Browser download |
| Import presets | System file picker | Browser file picker |
| Engine | Platform SQLite (Android) / system `libsqlite3` (iOS) | wa-sqlite (SQLite 3.44) |
| `dbstat` sizes | When compiled in | Estimated from data |

## Build & run locally

```bash
npm install                 # wa-sqlite + wrangler (dev dependencies)
npm run web:build           # → site/
npm run web:dev             # build + http://localhost:8788 with the production headers (CSP) applied
```

`site/?demo` opens straight into the demo database, a fictional field-service app generated by `web/demo/make-demo-db.py` in the shape of an OutSystems local storage database.

The page itself isn't forked for the web. `web/build.mjs` takes `www/inspector/db-inspector.html` and injects `host.js`, `host.css` and a few meta tags. The inspector only needs its generic host hooks:
- `window.DbInspectorHost` as the bridge;
- `context.canAddFiles` / `context.canClose`;
- the `addFiles` action;
- `window.__dbiDatabasesChanged`.

## Deploy to Cloudflare Pages

`wrangler.jsonc` defines the Pages project (`db-inspector`, output `./site`).

```bash
npx wrangler login                       # once
npx wrangler pages project create db-inspector --production-branch main   # once
npm run web:deploy                       # build + upload site/ (uses wrangler.jsonc)
```

The public site uses the custom domain `db-inspector.hfps.dev`, added in the Cloudflare dashboard under *Workers & Pages → db-inspector → Custom domains*. With the zone in the same account, the dashboard creates the CNAME to `db-inspector.pages.dev`.

For automatic deploys from GitHub, connect the repository in the Pages dashboard with build command `npm install && npm run web:build` and output directory `site`. The build needs Node 18+ and Python 3, both present in the Pages build image.

## Browser support

The site needs module Web Workers, `FileReaderSync` and WebAssembly: current Chrome, Edge, Firefox and Safari 15+. It was verified in Chromium: landing, demo database, the 433 MB OutSystems database, WAL overlay (compared against native `sqlite3`), merged export, query builder, `EXPLAIN`, cancel, and light/dark and phone layouts.

## Files

```
web/host.js            page-side host: bridge, files, downloads, localStorage, landing, drag & drop
web/host.css           landing / drag & drop styling (uses the inspector's design tokens)
web/worker.js          the engine: actions over wa-sqlite
web/lazy-file-vfs.js   read-only lazy File VFS with WAL overlay
web/build.mjs          builds site/ and _headers (CSP with the inline script hash)
web/demo/make-demo-db.py   fictional demo database
wrangler.jsonc         Cloudflare Pages project
```
